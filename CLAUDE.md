# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

FastAPI To-Do List API built with a Clean Architecture layering, used as a learning project (the author is an experienced PHP/Laravel developer learning Python/FastAPI/SQLAlchemy by building this). Python 3.12, managed with `uv`.

## Commands

All commands run via `uv run <cmd>` (do not assume a global install; the venv is managed by `uv`).

### Running the app

```bash
docker compose up -d --build   # starts the API (localhost:8000) + Postgres, with hot-reload via a volume mount on ./src
docker compose logs -f api
```

The app can also run against the same Postgres instance directly on the host (`.env` already points `POSTGRES_HOST` at `localhost`, since the port is exposed by `docker compose`):

```bash
uv run uvicorn src.main:app --reload
```

### Tests

```bash
uv run pytest                                  # full suite (integration + unit)
uv run pytest tests/test_todos.py              # one file
uv run pytest tests/test_todos.py::test_name   # one test
uv run pytest tests/unit/                      # unit tests only
```

Integration tests (`tests/test_todos.py`, `tests/test_categories.py`) hit a real (in-memory SQLite, via `aiosqlite`) database through the full FastAPI stack, using the `client` fixture from `tests/conftest.py`, which overrides the `get_db_session` dependency. Unit tests (`tests/unit/`) isolate a single `*Service` class by injecting `unittest.mock.AsyncMock` in place of its repository dependencies — no database involved. When adding a new service method with real SQL logic (filtering, joins, ...), prefer an integration test, since mocking the repository proves nothing about the query itself; reserve unit tests for the service's own branching/orchestration logic.

### Lint & format

```bash
uv run ruff check .            # lint (rules: E, F, I, UP, B — see pyproject.toml)
uv run ruff check --fix .
uv run ruff format .
```

Ruff targets `py312` — use native 3.12 syntax (e.g. `class Foo[T]:` generics, not `TypeVar`/`Generic`) rather than older-but-still-valid patterns.

### Database migrations (Alembic)

```bash
uv run alembic revision --autogenerate -m "description"
uv run alembic upgrade head
uv run alembic current
```

`alembic/env.py` imports every module's `models.py` explicitly so Alembic's autogenerate can see all tables — a new module's models must be added there too. Always review an autogenerated migration before applying it (Alembic's default template is not `py312`/Ruff-compliant — imports and `Union[...]` type hints typically need fixing to match the rest of the codebase, and `ruff check --fix`/`ruff format` should be run on the generated file).

## Architecture

### Module layering (Clean Architecture)

Each domain lives under `src/modules/<name>/` with the same four files, in strict call order:

```
router.py → service.py → repository.py → models.py
```

- **`models.py`** — SQLAlchemy 2.0 declarative models (`Mapped[...]`, `mapped_column`). No business logic.
- **`repository.py`** — the only layer that builds/executes SQL (`select`, `.where`, etc.). Takes and returns ORM model instances or primitives; never raises HTTP-related errors, never imports Pydantic schemas beyond what's needed to type method inputs (e.g. `*Create`/`*Update`).
- **`service.py`** — business/orchestration logic (uniqueness checks, resolving foreign IDs into objects, deciding what to eager-load). Depends on one or more repositories (a service can depend on another module's repository — e.g. `TodoService` also takes a `CategoryRepository` to resolve `category_ids`). Raises the custom exceptions from `src/core/exceptions.py`, never `fastapi.HTTPException` — the service layer must stay framework-agnostic.
- **`router.py`** — FastAPI endpoints. Owns the dependency-injection factory (`get_<name>_service`) and the `*ServiceDep` type alias for each module. This is also where request validation (via the request schema type hint) and response serialization (via `response_model`) happen — schemas are read/written here, not deeper in the stack. Convention: in a handler's signature, the injected service dependency is listed **before** the request-body parameter.

`src/core/` holds cross-cutting pieces used by every module: `database.py` (async engine/session, `Base`, the `get_db_session` FastAPI dependency), `config.py` (`pydantic-settings`, reads `.env`), `exceptions.py` (`NotFoundError`, `ConflictError` — generic, not per-resource) and `schemas.py` (the generic `PaginatedResponse[T]`).

### Cross-module relationships

`todos` and `categories` are many-to-many, backed by a third module, `src/modules/todos_categories/`, holding only the SQLAlchemy association `Table` (not a mapped class — it has no columns beyond the two FKs, both `ON DELETE CASCADE`). `Todo.categories` / `Category.todos` are declared via `relationship(secondary=todos_categories, back_populates=...)`.

Since `todos/models.py` and `categories/models.py` need each other's class for the relationship's type hint, the cross-import is done under `if TYPE_CHECKING:` with the target class referenced as a string (e.g. `Mapped[list["Category"]]`) — SQLAlchemy resolves the string lazily once all mappers are configured, so no runtime import is needed and no circular-import risk exists. The `secondary=todos_categories` table object, by contrast, *is* needed at class-body evaluation time, so it's imported normally (safe here because `todos_categories/models.py` only references `"todos.id"`/`"categories.id"` as FK strings, never importing the `Todo`/`Category` classes themselves).

`todos/schemas.py` imports `CategoryResponse` from `categories/schemas.py` directly (one-directional, safe) to build `TodoDetailResponse` (`?include=categories` on `GET /todos/{id}`). The reverse (a category's todos) is deliberately **not** modeled as a nested Pydantic schema — it's exposed instead as its own endpoint, `GET /categories/{id}/todos` → `PaginatedResponse[TodoResponse]`, precisely to avoid the schema-level circular import that a `CategoryDetailResponse` referencing `TodoResponse` would reintroduce (Pydantic can't auto-resolve such a cycle the way SQLAlchemy does; it needs an explicit `model_rebuild(_types_namespace=...)` call — deemed not worth the complexity here).

That same endpoint is also an example of a **router depending on another module's service**, not just a service depending on another module's repository: `categories/router.py` imports `TodoServiceDep` from `todos/router.py` and delegates to `TodoService.list_todos(category_ids=[category_id], ...)` rather than re-implementing pagination/filtering against `Category.todos`. `CategoryService.get_category_or_404` is still called first, purely to get a real 404 when the category itself doesn't exist (`GET /todos?category_ids=<missing>` would otherwise just return an empty page, not an error). This is safe the same way the schema-level import is: `todos/router.py` never imports anything from `categories/router.py`.

### Optional includes and pagination

Detail endpoints that can optionally return a related collection (e.g. `GET /todos/{id}`) take an `include` query param (`list[str] | None = None`, never a mutable `[]` default) and branch between two response schemas (`response_model=TodoResponse | TodoDetailResponse`), constructing the right one explicitly with `.model_validate(...)` in the handler — FastAPI can't infer which union member to use on its own. The repository method backing this takes a `with_<relation>: bool = False` flag that conditionally adds a `selectinload(...)` option to the query.

List endpoints (e.g. `GET /todos`) return `PaginatedResponse[T]` (`src/core/schemas.py`) rather than a bare list, so `response_model` on those routes must be `PaginatedResponse[TodoResponse]`, not `list[TodoResponse]` — the two are not interchangeable and mixing them up produces a `ResponseValidationError`, not a silent wrong response. The service returns `tuple[Sequence[Model], int]` (items, total); the router builds the envelope. Repositories expose matching `get_all(...)`/`count(...)` methods that both funnel their filter conditions through a shared private `_apply_filters(query, ...)` helper, so the two queries can never drift out of sync. Multi-value filters on a many-to-many field (e.g. `category_ids`) use union/OR semantics (`Model.relationship.any(Other.id.in_(ids))`), which is the standard convention for repeated query params. Free-text filters (e.g. `name`, `title`) use `Column.ilike(f"%{value}%")` — portable case-insensitive partial match across Postgres and the SQLite used in tests (SQLAlchemy compiles it to native `ILIKE` on Postgres, `lower(...) LIKE lower(...)` elsewhere), with `Query(min_length=2, ...)` to keep single-character searches from matching everything.
